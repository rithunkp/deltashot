## 1. Project Summary

**Title:** DeltaShot — Reference-Conditioned Neural Compression for UI Screenshot Sequences

**One-line pitch:** JPEG, WebP, and even recent domain-specialized neural codecs compress every UI screenshot independently. Platforms that store UI screenshots over time (visual regression testing, CI artifacts, versioned docs) almost always already have an earlier "baseline" screenshot of the same page sitting on the server before a new one arrives. DeltaShot compresses a new screenshot *conditioned on* that already-available baseline, so unchanged or lightly-changed regions cost almost nothing to encode, while gracefully falling back to standalone compression when the baseline isn't useful (first-ever screenshot, unrelated page, full redesign).

**Team:** Rithun K P (AM.SC.U4AIE24041), Balagopal V (AM.SC.U4AIE24012), Saavan Rajeev (AM.SC.U4AIE24065) — B.Tech CSE (AI) capstone project.

**Target output:** a working trained system + benchmark results + short technical report, scoped to be achievable by a 3-person student team with limited time/compute. The primary study may use the existing balanced WebSight-derived synthetic mutation corpus; all reports, demos, and presentations must identify it as synthetic and scope conclusions to it. Real screenshot-history validation is useful future work, but is not required to complete this constrained v1. Prioritize a working, honestly-evaluated v1 over an ambitious but incomplete system — see Section 9 (Scope Discipline).

## 2. Core Research Question

> **Given a target UI screenshot and a reference screenshot of the same page/component from an earlier point in time (already available at both encoder and decoder), how much smaller can we make the target's compressed file — at matched reconstruction quality — by conditioning compression on that reference, compared to compressing the target independently? And does this gain hold up gracefully (i.e. never get *worse* than independent compression) when the reference turns out to be unrelated or the page has been completely redesigned?**

This is **not** a video compression problem: the reference and target are not dense frames with small predictable motion between them. They may be:
- Pixel-identical (nothing changed)
- Near-identical with one small localized edit (a color, a button, a line of text)
- Substantially different due to a layout reflow caused by a small edit (e.g. adding a paragraph pushes everything below it down)
- Completely unrelated (full redesign, or the "reference" is actually a different page)

No assumption of small spatially-local motion can be made, so classical motion-compensation (the core trick in video codecs) does not directly transfer. The system must learn to detect and exploit *arbitrary content-level similarity*, not motion.

---

## 3. Why This Is Novel (read before implementing — do not accidentally re-solve an already-solved problem)

Literature check performed prior to this spec (see Section 11 for full references):

1. **Domain-specialized screen-content compression already exists and is well-validated.** Zamanshoar Heris & Bajić (2023), *"Multi-Task Learning for Screen Content Image Coding,"* shows that retraining/adapting a learned codec specifically for screen content yields 36–62% smaller files vs. a natural-image-trained codec at matched quality, beating even HEVC-SCC and VVC. **Do not present "a neural codec beats JPEG on screenshots" as the novel claim — it is not novel, it is already published.** That paper's method compresses every image **independently** — it never uses another image as a reference. That is the gap this project fills.

2. **Reference-conditioned / cross-image compression exists, but not for this data regime.**
   - Video compression (e.g. Li, Li & Lu, *"Deep Contextual Video Compression,"* NeurIPS 2021 — the "DCVC" line) does reference-conditioned coding extremely well, but assumes dense, regularly-sampled frames with small motion. UI screenshot histories are sparse, irregularly spaced, and have no motion structure.
   - Mital et al. (2023), *"Neural Distributed Image Compression with Cross-Attention Feature Alignment"* (WACV), compresses an image using a correlated image as decoder-side side information — closest existing technique — but is evaluated on stereo image pairs / nearby video frames, which have *guaranteed* strong spatial correlation. UI screenshots reference pairs have *unpredictable* correlation (could be identical, could be unrelated).

3. **The actual gap:** nobody has combined domain specialization (for screen/UI content) with reference-conditioning (for cross-image redundancy) in a setting where the reference-target similarity is highly variable and unknown in advance, and validated it against a real, concrete downstream use case (visual regression testing / CI screenshot storage, where this exact scenario — "we already have a baseline, here's a new screenshot" — is the literal existing workflow).

**When writing the report/paper, always frame the contribution this way — combination + new data regime + concrete deployment scenario — not "we compress screenshots with a neural net," which is already done.**

## 4. System Architecture

### 4.1 High-level pipeline

```
reference image (already stored) ──► Reference Feature Extractor ──► F_ref (multi-scale features)
                                                                            │
target image ──► Conditional Encoder ◄── Alignment Module (cross-attention: target queries F_ref) ── C (context)
                        │
                        ▼
                  latent y ──► Conditional Entropy Model (probability of y, conditioned on C) ──► bitstream
                        │
                        ▼
                  Conditional Decoder (uses decoded y + C) ──► reconstructed target image
```

In parallel: a **No-Reference Codec** (standalone domain-specialized codec, no conditioning) is trained as both (a) a baseline for comparison and (b) the fallback path used by Mode Selection.

### 4.2 Components, in build order (build in this order — each is testable independently)

1. **Backbone blocks** (`models/backbone.py`): standard conv + GDN/IGDN layers (as in Ballé et al. 2017 / used throughout CompressAI). Reuse CompressAI's implementations rather than writing from scratch — see Section 7 (Dependencies).

2. **No-Reference Codec** (`models/baseline_codec.py`): a standard hyperprior codec (Ballé/Minnen-style: analysis transform → quantize → hyperprior entropy model → synthesis transform), trained on screen-content images only, no conditioning. **Build and validate this first** — it's the SFU-paper-equivalent baseline, it's the fallback path, and it's the easiest piece to get working end-to-end. Suggested starting point: CompressAI's `bmshj2018-hyperprior` or `mbt2018-mean` architecture, retrained from scratch (or fine-tuned) on the screenshot dataset from Section 5.

3. **Reference Feature Extractor** (`models/reference_encoder.py`): shares early conv layers with the No-Reference Codec's analysis transform (weight sharing is fine and reduces params), producing feature maps at multiple downsampling scales (e.g. 1/4, 1/8, 1/16) from the reference image only. This runs once per reference and can be cached/reused across many targets sharing the same baseline.

4. **Alignment Module** (`models/alignment.py`): **v1 (build first, simple):** no alignment — just feed `F_ref` at matching spatial resolution directly into the conditional encoder/entropy model as extra input channels. This is a valid, working baseline for "reference conditioning" and should be benchmarked before adding complexity. **v2 (add after v1 works):** cross-attention block where each spatial location of the target's intermediate features queries `F_ref` to find the best-matching reference content, following the approach in Mital et al. (2023). To keep compute tractable, restrict attention to local windows (e.g. a K×K neighborhood in feature space) rather than full global attention — global attention over full feature maps will likely be too slow/memory-heavy for a student compute budget.

5. **Conditional Encoder/Decoder + Entropy Model** (`models/conditional_codec.py`): analysis transform takes the target image *and* the context `C` (from step 3/4) and produces latent `y`. The entropy model's probability estimate for `y` is conditioned on `C` (this is the "conditional coding" idea from DCVC — condition the *entropy model*, not just do pixel subtraction; this is why it beats naive residual/delta coding). The synthesis transform (decoder) reconstructs the target from decoded `y` and `C`.

6. **Mode Selection** (`models/mode_selection.py`): for a given (reference, target) pair, estimate the bitrate under both the Reference-Conditioned Codec and the No-Reference Codec (both are cheap to run), and transmit whichever is smaller, plus a 1-bit flag indicating which mode was used. This guarantees the system is never meaningfully worse than the No-Reference baseline. **This is a required component, not optional** — it's what makes the graceful-degradation claim in the problem statement true, and it's part of the ablation story.

### 4.3 Loss function

Standard rate-distortion loss, per training example:

```
L = R + λ * D
```

- `R` = estimated bits to encode `y` (and hyperprior `z` if used), from the entropy model's likelihood.
- `D` = distortion between reconstructed and original target image. Use MSE as the primary metric (standard, comparable across literature); also log MS-SSIM for reporting.
- Train **separate models at multiple λ values** for v1 (simpler, matches original Ballé/Minnen methodology). Suggested starting λ set (typical CompressAI convention, adjust based on observed bitrates): `{0.0018, 0.0035, 0.0067, 0.0130, 0.0250, 0.0483}`.
- *(Optional stretch goal, only after v1 fully works: a single variable-rate model conditioned on λ via FiLM modulation, avoiding the need to train N separate models. Do not attempt this until the fixed-λ version is fully benchmarked.)*

## 5. Data Pipeline

### 5.1 Primary dataset: synthetic mutation sequences

**Source:** base pages from `HuggingFaceM4/WebSight` (v0.2), CC BY 4.0 — reuse the filtering/rendering pipeline already built in the team's earlier project (Easy-UI), including the headless-browser rendering setup.

**Generation process:**
1. Take a base HTML/CSS page from WebSight. Render it → this is `version_0` (the reference).
2. Apply one randomly sampled mutation operator (implement each as a separate function in `data/mutations/`):
   - `mutate_color`: change a CSS color property (background/text/border) on a randomly chosen element.
   - `mutate_text`: edit, add, or remove text content in a randomly chosen text node.
   - `mutate_layout`: change a size/margin/padding/display property that causes downstream reflow.
   - `mutate_insert`: insert a new element (button, image placeholder, paragraph, etc.).
   - `mutate_remove`: remove an existing element.
   - `mutate_replace`: swap in a **completely different, unrelated** base page (this generates the "reference is useless" training examples — critical for teaching graceful degradation).
3. Render the mutated page → this is `version_1` (the target). Save the `(reference, target)` pair.
4. For variety, also generate longer chains (e.g. 5 sequential mutations) and pair non-adjacent versions (e.g. `version_0` with `version_4`) to get pairs with larger, more realistic cumulative change — don't only use adjacent-version pairs, or every example will look artificially small-change.
5. **Label every pair with a degree-of-change bucket**, computed via a cheap proxy (pixel-difference percentage or SSIM between reference and target):
   - `identical` (~0% pixels changed)
   - `minor` (<2%)
   - `moderate` (2–15%)
   - `major` (15–50%)
   - `unrelated` (>50%, or explicitly from `mutate_replace`)

   **This bucketing is required, not optional** — it's how the ablation (Section 6) and the headline results are broken down. Store the bucket label alongside each pair's metadata.

**Target size:** aim for a similar order of magnitude to the earlier project's dataset (e.g. ~20k pairs train / ~2k val / ~2k test), roughly balanced across degree-of-change buckets — don't let `identical`/`minor` dominate just because they're easy to generate, or the model won't get enough signal on harder cases.

### 5.2 Secondary dataset: real versioned screenshots

Collect a smaller validation set of **real** screenshots of the same UI component/page across different released versions, from public component-library / Storybook-style deployments (many open-source design systems publish versioned, publicly browsable Storybook builds). This checks whether results generalize beyond synthetic mutations, which is important since synthetic edits may not fully reflect how real UIs change over time. **Flag honestly in the report if this set ends up small** — it's a validation/generalization check, not the primary training data, so a modest size (even a few hundred pairs) is acceptable as long as it's disclosed as a limitation.

### 5.3 Out-of-domain sanity check

Standard Kodak (24 images) and CLIC benchmark sets, used only to confirm the No-Reference Codec's fallback behavior is reasonable relative to published generic learned-codec numbers (sanity check, not a core result).

### 5.4 Suggested directory layout

```
data/
  raw_websight/            # cached filtered WebSight pages (reuse from Easy-UI project)
  mutations/                # mutation operator implementations (one file per operator)
  synthetic_pairs/
    train/ val/ test/       # each entry: reference.png, target.png, meta.json (bucket label, mutation type, chain position)
  real_pairs/                # scraped real versioned screenshots, same pair format
  benchmarks/
    kodak/ clic/
```

## 6. Baselines and Evaluation Protocol

### 6.1 Baselines to implement (in this priority order)

1. **JPEG / WebP** — via Pillow / `libwebp`, standard quality sweeps.
2. **No-Reference Codec (this project's own domain-specialized codec)** — Section 4.2 step 2. This is the primary "fair" baseline — same training data, same general architecture family, just without conditioning.
3. **Generic pretrained learned codec** — a CompressAI pretrained checkpoint (trained on natural images, e.g. Kodak-style), run as-is on screenshots, to show the domain-specialization gap still exists independent of this project's own contribution.
4. **Naive delta baseline** — pixel-difference between reference and target, then compress the difference image with PNG/gzip. Cheap to implement, useful as a "dumb" reference-conditioning baseline to show that naive differencing is *not* sufficient (this is the same point DCVC makes about residual coding vs. conditional coding — include it to make that point concretely in this project's own domain).
5. *(Optional, time permitting)* — a real video codec (e.g. libx264/libx265) fed the `[reference, target]` pair as a 2-frame "video," as an upper-bound sanity check from an unrelated but mature technology.

### 6.2 Metrics

- **PSNR** and **MS-SSIM** vs. bitrate (bits per pixel), producing standard rate-distortion curves.
- **BD-rate** (% file size difference vs. a baseline at matched quality) — the single-number headline metric, computed against each baseline in Section 6.1.
- All of the above **broken down by degree-of-change bucket** (Section 5.1) — this breakdown is the actual proof of the core claim, not just an aggregate number.

### 6.3 Required ablation

Compare, at matched quality, across degree-of-change buckets:
- Reference-Conditioned Codec (full system, with Mode Selection)
- No-Reference Codec alone
- Reference-Conditioned Codec **without** Mode Selection (i.e. always forced to use the reference, even when unrelated) — this shows *why* Mode Selection is necessary, by showing performance would degrade badly without it in the `unrelated` bucket.

**Expected/success pattern** (what a positive result looks like): large BD-rate improvement over the No-Reference baseline in `identical`/`minor`/`moderate` buckets, shrinking in `major`, and statistically indistinguishable (not worse) in `unrelated` — because Mode Selection falls back correctly. If the `unrelated` bucket comes out *worse* than the No-Reference baseline, Mode Selection has a bug — treat this as a correctness bar, not just a nice-to-have result.

## 10. Open Risks / Things to Watch For

- **Alignment cost:** full cross-attention over feature maps may be too slow/memory-heavy on student-grade compute. Mitigate with local/windowed attention (Section 4.2 step 4).
- **Synthetic mutation realism:** procedurally generated edits may not fully reflect how real websites change over time. This is why Section 5.2 (real validation set) exists — treat it as a required sanity check even if small, not an optional extra.
- **Dataset imbalance:** if `identical`/`minor` pairs dominate the dataset (they're the easiest to generate), the model may not learn to handle `major`/`unrelated` cases well. Actively balance the dataset across buckets (Section 5.1).
- **Mode Selection correctness is the single most important thing to get right** — a bug here silently breaks the "never worse than baseline" claim, which is central to the whole pitch. Add an explicit automated test that checks BD-rate in the `unrelated` bucket is not worse than the No-Reference baseline before considering Phase 6 done.
